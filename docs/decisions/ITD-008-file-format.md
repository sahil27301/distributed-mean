| ITD 8 - *Use integer values in raw little-endian int32 binary files* |  |
| :---- | :---- |
| **THE PROBLEM** | What value type and encoding do we use for input files, partials, and the result? |
| **OPTIONS CONSIDERED (Decision in bold)** | ***Integers 0–999. Inputs and partials: raw int32 little-endian. Result: CSV of float64 means*** <br> CSV everywhere <br> Floats in [0, 1] as raw float64 <br> `.npy` <br> Parquet |
| **REASONING** | Integers make sums exact, so results are deterministic and tests can compare with equality, regardless of merge order. <br> Encoding dominates the work: summing 5 × 1M values in numpy takes milliseconds, while parsing 1M values from CSV takes on the order of 0.1–1 s (estimate). A job does ~1.25 F file reads, so CSV makes the system parse-bound. Raw binary decodes with `np.fromfile(path, dtype='<i4')` at memory/disk speed. <br> One dtype for every file means one read/write code path, and no header: `files_covered` lives in the DB. The largest possible sum is 999 × 100k ≈ 1e8, well under the int32 limit (~2.1e9). <br> Node writes an `Int32Array` buffer directly. `.npy` needs header writing from Node for little gain. Parquet is overkill for one flat column. Floats lose exactness and double the size. The result is written once and read by humans, so CSV is fine there. |
| **TRADEOFFS** | Intermediate files aren't human-readable; inspecting them needs a small script. <br> The dtype and endianness contract between Node and Python must be documented and tested. <br> If value bounds or F grow, sums can overflow; the API rejects jobs where max value × F ≥ 2^31. <br> Integers deviate from the problem's "between 0 and 1" example, which it explicitly allows us to choose. |
| **NOTES** | File size at C = 1M: 4 MB for both inputs and partials. Workers sum in int64 in memory and assert the result fits int32 before writing. |
