| ITD 4 - *Claim 2–5 items per task, largest partials first* |  |
| :---- | :---- |
| **THE PROBLEM** | When does a worker claim work for a job, how many items, and which ones? |
| **OPTIONS CONSIDERED (Decision in bold)** | ***At least 2, up to 5, ordered by `files_covered` descending*** <br> Wait until exactly 5 are available <br> At least 2, raw files first (oldest first) <br> Claim even a single item |
| **REASONING** | Claiming 1 item is a no-op merge that gets re-queued forever near the end of a job. <br> Waiting for exactly 5 leaves workers idle while partials trickle in. <br> Every task produces 1 partial; what differs is how many partials it consumes. Largest-first means partials are consumed as soon as they appear, so partials on disk stay around W (≤ ~5W counting in-flight). Raw-files-first builds an entire level before consuming it, peaking at ~F/5. <br> Simulated with identical and with random worker speeds: both orders finish in the same time with the same idle slots. Only storage differs. |
| **TRADEOFFS** | Fan-in below 5 near the end of a job adds a few extra merges. <br> When only 1 item is visible, workers move on or poll. <br> The tree is unbalanced (one partial snowballs), which is irrelevant with integer sums. |
| **NOTES** | Storage at max scale (F = 100k, C = 1M, int32 → one partial = 1M × 4 B = 4 MB, W = 10): <br> Raw-files-first: all F/5 = 20k first-level tasks run before any partial is consumed → 20k × 4 MB ≈ 80 GB. <br> Largest-first: ~W partials waiting → 10 × 4 MB = 40 MB; ≤ ~5W = 50 partials ≈ 200 MB counting inputs held by in-flight tasks. <br> Task count is the same either way: each 5-way merge removes 4 items, F items reduce to 1 → (F − 1) / 4 ≈ 25k tasks. |
